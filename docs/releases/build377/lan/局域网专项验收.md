## 同一台浏览器同时登录两个端口

在同一主机分别启动两份合法的合成 DSHA，浏览器使用同一份 cookie 存储先后登录两个地址，分别打开 WebSocket，交替刷新四次，再分别开一次 WebSocket。每个服务只记录实际收到的授权头、有效会话是否存在，以及调用密码 KDF 的次数。全部记录都没有密码、会话值、请求正文。Chromium 只给两把预先核实的合成公钥设置测试例外。Firefox 使用临时测试上下文的证书例外，页面请求限制在两条回环地址。这里比较登录连续性，首次证书校验另有 Chromium 与 Android 系统证据。

## WebKit 实时连接与单次票

Windows WebKit 26.5 在普通 HTTPS 请求得到 401 后会重新发送已缓存的 Basic 凭据，但在 WSS 握手中不送 Basic。仅要求 cookie 加 Basic 的中间版本中，同一浏览器的两个端口都可登录，连续四次 HTTP 刷新都是 200，四次 WSS 却都失败。两个服务端各自见到两个带正确会话、缺 Basic 的 WebSocket 握手。这是可重现的功能缺口。[失败轮](dual-after-1795591073/report.json) · [服务端只记有无的记录](dual-after-1795591073/service-1.log)

最终代理允许网页带当前端口 cookie 和该来源的 Basic，向 `POST /__dsha/lan/ws-ticket` 申请短票。请求必须来自完全相同的 HTTPS 来源、没有正文，并声明目标路径。服务器将 32 字节随机值绑定该监听、用户会话与路径，有效期 60 秒，最多 16 份待用票/会话、256 份/监听。WebSocket 的子协议带票，服务在转发前同步消耗一次。用户已有的子协议保持顺序并由原后端选择。无原子协议时外层用固定占位应答，后端不见票据或占位。诊断会隐藏票据和子协议头。WebKit 的 HTTPS 挑战会保留仍然有效的会话，以便它带 Basic 重试。登录失效时只清理本端口 cookie。[发票与单次消费](../../../../app/src/main/java/com/deepseekharness/app/util/LanTokenState.java) · [协议转发](../../../../app/src/main/java/com/deepseekharness/app/LanWebSocketProtocols.java) · [监听与端点](../../../../app/src/main/java/com/deepseekharness/app/LanProxyService.java#L700)

真实 DSH 页面首次进入和快速刷新时会同时启动 SSE、WebSocket，加载 JS、CSS 并调用多个小 JSON 接口。Node 的普通 JSON、脚本和样式也常使用 HTTP 分块编码。原代理把这些响应和长期订阅送进同一组 8 个流工作线程。浏览器关闭 SSE 时，后端若一直等新事件，代理此前只在下次向浏览器写数据时才会发现断开。用户因此可能看到部分设置缺项，甚至关键页面 JS 返回 503。

以提交 `e9c96aad` 进行正常 Firefox、WebKit、Chromium 的初进和刷新，各 2 轮。仅首个 Chromium 独立运行的控制组没有拒绝，但退出前仍留 2 条 SSE。三浏览器依次运行时，拒绝全出现在长流准入，9 次拒绝，浏览器观察到 6 项 `proxy-busy`。其中 Chromium 两轮分别为 1、5 项，拒绝时实际已有多条长达数秒的旧 SSE，加上正在发送的普通 JSON 或脚本。监听页面进程结束前还留 6 条 SSE。另两个真实快刷样本中复现了 `vendor-BUMdD3V7.js`、`list`、`modelCatalog`、`listProviders` 和 `syncInspectManifest` 等项目的代理自发 503。第一轮 Firefox 空白页的当时记录没有采失败头，后续两次快速刷新均成功，因此未将那一次空白单独归因为该问题。[原始调度记录](admission-before-r2/stages.log) · [同组浏览器记录](admission-before-r2/page/results.json) · [第一轮真实页面](../web-identity/lan-mux/real-r1/results.json)
