## 浏览器、数据和原始轮次

Windows 本机 Node 24.18.0 启动实际 rc.5 DSH Web CLI，覆盖所列 ARM64 归档中的代码和图片。该次临时配置只含官方 base/web bundle 以及合成账号，Node 只能连接回环。用真实 CLI 的本地登录入口换取该临时实例的后端会话，通过标准输入交给真实生产 LanProxyService。浏览器使用单独的合成 LAN 登录。Chromium 明确固定临时证书的 SPKI。Firefox 和 WebKit 的独立测试上下文接受该自签回环证书，故这两项测到的是认证实时传输；未测系统信任库安装该证书的流程。Java 宿主替代 Android 密钥托管和系统网络信息。没有录制帐户正文、私密 URL、认证头、Cookie、票据或业务帧载荷。每个浏览器实开工作台、检测真实侧栏节点和双向帧，再刷新。应急归档和正式归档均在本机普通 Web profile 执行，Android 应急页面的启动另见总报告。

R4 正式归档的完整三引擎轮次如下。帧数为上行/下行，计至首批功能验收完成；时间从该次导航开始计，分别为首份 HTML 和侧栏及真实双向业务帧全部得到确认的时间。新装页、已有 profile 或系统设备均可能有不同耗时。

| 实际引擎 | 首次进入，帧数；HTML / 全部 | 同窗口刷新，帧数；HTML / 全部 |

## 已知失败和范围

首次真实页面测试中，Firefox 的初次页面渲染与双向帧均成功。侧栏刚出现即快速刷新，取得 HTML 200，但 40 秒内未进入 RPC/取票或渲染侧栏。这轮诊断仅记录 API 状态，不能单凭它还原原因。旧夹具在 DSH 进程退出前回收临时目录，又产生 Windows PermissionError；该目录最终核实为空，移除空目录的自动审批返回 blocked by policy。后续夹具先关闭子进程再删除临时目录。正式页面稳定后刷新及一次独立的 Firefox 快速刷新复验全部通过。[原始失败](real-r1/results.json) · [快速刷新复验](real-r3-immediate/results.json)

已从真实响应确认并发取网页资源偶尔会得到代理自身的 503。在 R4 应急归档使用同一 Java 实例依次测试 Firefox、WebKit、Chromium 时，Chromium 两轮分别出现 2 个、11 个 `proxy-busy` 响应，涉及 vendor JS 及部分前端 API，实时 mux 自身两轮成功。另一次从 Chromium 开始的 6 轮均未出现这些拒绝。它是页面并发访问的额外观测，不能把每个页面 200 或实时连接 101 解释为所有功能调用都成功。[忙响应类别与诊断头](real-r3-rescue/results.json) · [生产代理并发快照](real-r4-metrics/results.json)

按可复现的 Firefox→WebKit→Chromium 顺序再次采集时，Chromium 两轮分别出现 3、7 个 proxy-busy，连接调度器累计拒绝由 0 到 2 再到 13，连接峰值由 10 到 11 再到 12。这轮额外记录了前后端各有一个实际业务帧的首个时间点及完整验证时间。[首个双向帧、逐轮调度快照与失败响应](real-r5-metrics/results.json)
