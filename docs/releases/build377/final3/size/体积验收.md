## 两个工具能否完整读回

`encode_tool_archive` 保留两份固定上游 gzip 中完整的 TAR 文件流，给 XZ 的 LZMA2 编码器使用 ARM64 四字节对齐的位置参数。Android 解码字典沿用 1 MiB。Windows 宿主用 Java 25.0.4、XZ 1.12、`-Xms32m -Xmx96m`，通过项目的 `BundledRootfsAsset.decode` 与 `LegacyTarReader.readTrustedAssets`，直接读取从两个签名 APK 提取的载荷。两个工具、新旧两包各交替三遍，共 **12 次**均读到 EOF，整条 TAR 的 SHA-256 均与上游原件相同。[编码函数](../../../../../tools/prepare-standard-assets.py) · [生产解码器](../../../../../app/src/main/java/com/deepseekharness/app/util/BundledRootfsAsset.java) · [TAR 读取器](../../../../../app/src/main/java/com/deepseekharness/app/backup/LegacyTarReader.java) · [12 次原始记录及上游摘要](java-final.json)

## 为什么第二、第三次签包大小相同

第二次签名包 SHA-256 为 `72917c42dee81df41e26f2d7977ba735b0e3c0c94a93803561272d6f6facbeaa`，两个包均为 255,587,176 字节。1,883 个 ZIP 成员的名字、内容摘要、压缩方式和大小一致，另有 7 项变化。所有成员的包内占用从 255,322,724 变为 255,323,024 字节，增加 300 字节。整包扣除这些成员后，其余 ZIP 头、中心目录、对齐和签名块等合计从 264,452 降至 264,152 字节，恰好减少 300 字节。这项测量的精度到该部分的合计。[7 项变化与分层算式](second-third-apk-diff.json) · [第二次容量原件](../../final2/size/signed-size.json) · [第一次容量原件](../../size/signed-size.json)

## 重放

从工作区根目录用 PowerShell 运行。以下将复跑结果写入新目录。三个实际执行过的完整命令、已读回执和退出状态另见[执行原件](run.json)。专项最终三项均一次通过，早期打包夹具的失败、修订及复验保存在[阶段体积验收](../../size/%E4%BD%93%E7%A7%AF%E9%AA%8C%E6%94%B6.md)。

```powershell
$sizeTools = 'artifacts/build377-local/size'
$beforeApk = 'artifacts/build376-formal-20261125/signed/dsha-0.2.2-rc.5.apk'
$afterApk = 'artifacts/build377-local/signed-final/dsha-0.2.2-rc.5.apk'
$afterSha = '292f89da4d199c7364aba77b441370f7c75e276d65f11ecc82c29a6f60a45ba8'

python -B "$sizeTools/bind_signed_size.py" --runtime-round r4 $beforeApk $afterApk $afterSha $signedCommit "$replayDir/signed-size.json"
python -B "$sizeTools/check_tool_readback.py" $beforeApk source/build377-local source/build376-local/app/src/main/assets "$replayDir/java-final.json" --candidate-apk $afterApk
python -B "$sizeTools/inventory_apk.py" $afterApk $afterSha "$replayDir/b377-final"
```
