# 安装监督进程未收到启动确认

## 用户看到的变化

在一台 API 30、x86_64、通过原生桥运行 ARM64 二进制的 Android 模拟器上，build377 两次非交互冷安装停在 PROOT 检查。用户只看到 `Stream closed`。它发生在向专属安装监督进程送出启动确认的那一步，尚未开始收集来宾的输出。改后同一台模拟器显示了下面的实测诊断。

> 发送启动确认失败。安装监督进程已退出（退出码 137）。 当前 Android 系统为 x86，此版本支持 ARM64 Android。可在设置中查看诊断。

当宿主拿不到退出码时，提示会明确说退出状态尚未确认。架构提示要同时读到 Android 本机系统执行文件的 x86 / x86_64 ELF 头和这次实际运行的随包 AArch64 ELF 头才会出现。ARM64 Android 遇到普通断管不会收到 x86 提示。旧异常作为直接 cause 保留，面向用户的诊断只写阶段、查到的退出码及可核实的架构，测试用的私有字符串没有进入该诊断。[同一触发的原始栈](../cold-stream/process-r2/result.txt) · [改后中文和英文及原始 cause](../cold-stream/ackoverlay-r1/result.txt)

## 来源、修补与适用范围

- 首个签名候选绑定 Git `15e7fcc285121d67efdfad11ce688fc0a81dd392`，APK SHA-256 `2e6f0324ebe4b52b143dcb2bf04800b1ce73c106a53b567de1afdafca5dba3d9`，255,587,176 字节。该候选作为本专项的改前版本。稳定复现用普通 UID 的自有合成子进程，原签名应用 DEX 的 `IsolatedInstallProcess.start` 在 `getOutputStream().flush()` 收到 Android `ProcessBuilder.NullOutputStream` 的异常。这里未进入 `BoundedProcessRunner.collect` 或 `ProcessPipePoller`，两处均未改动。[签名与版本](../signed/apk-signing.json) · [成品冷安装的两次事件](../lan/cold-stage-events.json)
- 比较 Windows NDK 26.3.11579264 编译的 ARM64 和 x86_64 观测件，可看到旧启动器在转译 ARM64 的子进程第一次可见观测之前收到 SIGSEGV(11)。父端拿到 wait 状态 11 后，按本来就有的代码结束整组，Android 报领导进程退出码 137。同一台 Android 上，相同 C 源的 x86_64 子进程能进入 shell。普通 UID 原件 raw 对照 R3 没有区分三秒超时后的主动结束，保留 R3 并以补足 `natural_wait` 和 `harness_force` 的 R4 为判断依据。生产报错不会把这台模拟器的 SIGSEGV 推定成其他机器的原因。[原件 R4](../cold-stream/process-r4/result.txt) · [ARM64 wait 状态](../cold-stream/observearm-r1/result.txt) · [x86_64 同源码](../cold-stream/observex86-r1/result.txt)
