# DSHA 0.2.1-rc.5-20261115.1335-dsh0.2.2-rc.1 / build367

- APK 업데이트(M17): 이제 사용자가 직접 동작해야 업데이트를 확인합니다. 앱 시작, 앱으로 복귀, 창 포커스 획득, 업데이트 페이지 최초 열기에서 자동 확인이나 업그레이드 안내를 하지 않습니다. 애플리케이션 수준의 소유자가 다운로드와 직렬 작업 큐를 관리하며, 다시 생성된 페이지는 원래 작업을 계속 관찰합니다. 권한 및 설치 결과는 사용자의 원래 요청만 이어 가고, 만료된 콜백은 새 요청을 만들지 않으며, UNKNOWN 상태의 동작은 재실행하지 않습니다.
- 내장 플러그인 활성화(T2): 설치되어 있고 관리 대상 내용의 정확한 증명이 있는 내장 플러그인이 타사 가져오기 규칙에 잘못 걸려 활성화되지 않는 문제를 수정했습니다. 자동 기본 비활성화 표식은 사용자의 의도와 별도로 기록합니다. 사용자가 비활성화한 상태와 출처를 모르는 과거의 빈 표식은 업그레이드 후에도 유지합니다. 내장 dsh-web-mobile 3.3.5 버전과 기본 활성화 정책은 바뀌지 않습니다.
- 시작 복구(S1a/S1b): Kotlin으로 중지 사실을 섀도 관찰하는 기능과 순수 인계 계약을 추가했습니다. S1a는 사실만 기록하며 기존 중지 판정을 대체하지 않습니다. S1b는 비활성화할 플러그인을 지정하지 않은 보호된 복구의 좁은 경로에서만 인계 증명을 한 번 소비하며, 실행 전 현재 식별 정보와 현장 상태를 다시 확인합니다. 인계 진입 전 조건을 충족하지 못하면 원래 경로를 유지하고, 진입 후 UNKNOWN, 객체 변경 또는 권한 만료가 발생하면 즉시 차단합니다. 이를 캐시 미스로 취급해 재실행하지 않습니다. 일반 시작과 수동 중지는 원래 경로를 유지합니다. 모든 경로의 종료 증명이 아니며, PID나 포트만으로 프로세스를 종료하지 않습니다.
- 백업 스트림 브리지(A3): Rust envelope 스트림 브리지를 연결하고, 크기 제한 스트림·실패·정리 계약을 확정했습니다. 기본 백엔드는 여전히 JVM이며, Rust 경로는 기존 활성화 조건과 사용 가능 조건을 모두 충족해야 합니다. Rust를 선택한 스트림이 실패한 뒤 JVM으로 바꿔 다시 읽거나 쓰지 않습니다. v5 아카이브 형식, 무결성 확인, 복원 의미는 유지합니다. APK의 off 모드에는 Rust 라이브러리를 포함하지 않습니다. 실제 Android Rust 스트림이나 전원 손실 복구에 대한 기기 인수 검증 완료를 주장하지 않습니다.
- Kotlin 전환: contract 전체 영역의 18개 파일, M17의 4개 파일과 SAF 15개, 다운로드/전송 8개, 네트워크 상태 3개 Java 파일을 Kotlin으로 전환했습니다. 실제 Java 호출부와 기존 동작을 영역별로 확인했습니다. ABI 기록에는 가시성, final, 컴파일러가 추가한 멤버 등의 경계를 명시합니다. contract의 기존 Java record 7개는 record 메타데이터를 보존하지 않으므로 비트 단위 ABI 동일성을 주장하지 않습니다. SAF ‘앱 간 파일 접근’, 다운로드 큐, 복구/게시 및 네트워크 상태 규칙은 기존 의미를 유지하며, Manifest 권한이나 데이터 형식을 새로 추가하지 않습니다.
- A8-P1 엔지니어링 기반: 고정 도구 체인과 빌드 규약, 공통 소스 배치, 컴파일 출처 증명, 저장소 전체의 새로 실행한 테스트 결과 집계, 동결된 테스트 식별 기준 및 unit contract proof를 검증 관문에 포함했습니다. 생성기 소스와 93개 항목의 런타임 레시피를 동기화했습니다. 타사 고지 스캔은 build-logic까지 포함하며, release 워크플로의 off 옵션이 YAML 불리언으로 변환되는 문제와 주 Java 컴파일 증명 누락을 수정했습니다. 소스 위생 UUID 스캔은 이제 `.kt`도 포함합니다.
- Rust APK 후보: 명시적인 prebuilt dry-run 경로에 같은 커밋의 arm64 산출물 출처와 바이트 재현성 확인을 추가했습니다. 정식 후보는 off를 사용하여 Rust 라이브러리를 패키지에 넣지 않습니다. prebuilt Provider 경로의 기존 결함은 아직 해결되지 않았습니다. 네이티브 산출물 빌드나 호스트 차등 결과를 Android 로드 성공의 증거로 간주하지 않습니다.
