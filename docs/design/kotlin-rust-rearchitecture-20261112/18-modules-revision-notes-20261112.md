# 对《新生计划：18 个逻辑模块划分》v0.1 的修订建议

> 对象：《新生计划：18 个逻辑模块划分与 21 模块对照》v0.1（2026-11-12，sha256 `637e7217…`）
> 提出方：21 模块方案评审线　日期：2026-11-12
> 性质：**只标"需要改的地方"，不重写你们的方案**。背景是我方 13 项决策已定（ADR-0004），口径已冻结为 **21 状态模块 / 9 Gradle 模块 / 1 个 Rust crate**。
> 配套：对照表已填在我方《回复 v0.3》§1；本清单是它之后的增量修订项。
> **后续更新（2026-11-12）**：对方已澄清 Rebirth 定位与 Gecko 性质（见回复 v0.4 §11）；本文第 1、5 项的前提假设据此更新，其余项仍有效。

**一句话**：骨架可用，但有 **1 个定位问题 + 1 个自相矛盾 + 1 个口径问题 + 3 块缺失**。这 6 项改完，才适合进入"契约冻结"。

---

## 一、必须改（4 项）

### 1. 「Rebirth」到底是代号，还是新项目？（标题 / §六 / §十）

**原文**：

- 标题页："项目：DSHA 新生（Rebirth），代号嫩芽（Sprout）"
- §六："Rebirth 候选的正式自更新当前停用；CI 不是 App 内模块"

**问题**：这两种解读会导出完全相反的方案，而文档没有回答。

| 解读 | 后果 |
|---|---|
| A. 同一 `applicationId` + 同一签名的**迭代**，"Rebirth"只是代号 | 覆盖安装是唯一升级路径，I1–I10 维护门禁必须进方案；"停用自更新"只能限定为"停自动检查/下载/安装" |
| B. **新项目 / 新包名** | 与老用户没有覆盖关系，只能靠 v5 导出导入迁移，会丢 Keystore 加密的会话记录与设备授权；"覆盖更新兼容"这条需求本身不成立 |

**建议**：在文档开头补一句明确表述。如果是 A，请同时删掉/限定 §六 的"停用自更新"；如果是 B，请单写一节"数据迁移"，并接受"卸载重装"的用户代价。

**影响**：决定 F02、维护页、自更新这些模块到底存不存在。

---

### 2. C03 的结果态与你们自己的第 3 点意见矛盾（§三 C03）

**原文**：

> 派发前复核及统一执行结果：拒绝、未派发、成功、失败、取消、执行未知。

**问题**：你们给我们的第 3 点意见是"应分别说明：是否派发、执行是否确定、是否部分完成、效果是否验证、能否重试"。这条批评完全正确，但 C03 自己仍然是一个六项列表，等于用同一个维度表达五个独立问题——这正是"取消后可能已执行"被混淆的根源。

**建议**：与 §C03 同步改为正交字段：

| 字段 | 取值 |
|---|---|
| `dispatched` | NOT_DISPATCHED / DISPATCHED / UNKNOWN |
| `executed` | NOT_EXECUTED / EXECUTED / UNKNOWN |
| `partial` | NONE / PARTIAL / UNKNOWN |
| `effect` | VERIFIED / UNVERIFIED / UNKNOWN / NOT_APPLICABLE |
| `retry` | SAFE / NEEDS_NEW_OBSERVATION / NOT_SAFE / UNKNOWN |

枚举只作日志/界面投影；"取消"作为**事件**记录，不占结果态。

**影响**：A1 契约冻结（这是双方接口要对齐的第一项）。

### 3. 把"18"写成目标口径太早，且 §七 对 21 的来源猜错了（§七 / §八 / §十）

**原文**：

- §十："**目标讨论口径：18 个逻辑边界。**"
- §七："若其他范围完全一致，仅做以下拆分……则 18 + 2 + 1 = 21"

**问题**：

1. §七/§八 自己承认"差异可能是粒度/统计范围"、"对照表待填"，但 §十 已经把 18 写成目标数字。先冻结、后映射，顺序反了。
2. "18+2+1=21"的猜测不成立。我方 21 的实际来源是：**7 项 1:1 + 2 组拆分（C04→4、A02/A01→2）+ 1 组合并计数（UI 吸收 F01/F02/F04/F08 的呈现层）+ 6 项净新增**。拆分 A03/A06 只是其中一种可能，不是实际原因。

**建议**：把口径写成三层——**18 功能口径 / 21 状态口径 / 9 编译口径**，并注明"三者只做映射，不相减"；§七 的推测改为引用实际对照表（我方回复 §1 已填完）。

**影响**：对外口径漂移，外部开发者会把 21 读成"多做了 3 个功能"。

---

### 4. 缺三块"失败域"，不是粒度差异（全文 / §六 表格）

**原文**：§六 只说明"未单独计数≠删除能力"，但下面三项在全文没有任何归属，也没有失败边界：

| 缺的边界 | 现状 | 为什么不能只当"机制"塞进 C02/A02 |
|---|---|---|
| **覆盖更新与维护门禁（I1–I10）** | 只在 §六"更新/构建/发布"一行出现，且写的是"自更新停用" | 覆盖安装后必须进整屏维护页、旧树不得拉 Web、未确认旧会话只拦自动开始——这三条都是生产事故换来的；没有归属就会在重构中丢失 |
| **进程身份与退出证据** | 完全没有 | 出生身份、双次核验、停止证明被生命周期/终端/实体屏/虚拟屏/受管安装五方共用；不独立就会各建一套判据（停止语义已经改坏过三轮） |
| **桥与入站网络（3090）** | A02 只写出站与 LAN | 入站鉴权、端点集合、能力派发、SAF 授权簿是宿主对外面，失败域与出站相反 |

**建议（二选一）**：

- 加 3 个模块：覆盖更新门禁、进程身份与退出证据、桥与入站网络；或
- 在 C02 / A02 下写明子边界与失败语义（至少覆盖：维护页入口、旧会话不自动重放、不按裸 PID/端口/名称发信号、入站鉴权与出站分离）。

**影响**：不写这三块，18 模块方案无法落到现有代码上，也无法验收。

### 6. C02 的"布局保存与恢复"不能跟着"可插拔宿主"一起裁掉（§三 C02）

**原文**：

> 页面路由、首页卡片、布局保存与恢复。

**问题**：我方已定"内部工程模块化，不做可安装模块宿主"。按这个结论，C01/C02 的**注册表、贡献登记、停用清理**可以退化为编译期接口；但**布局保存与恢复**是真实的用户功能（重启恢复、排序、隐藏、桌面卡片位置），不是可插拔能力。

**建议**：把它从 C02 的"宿主能力"里拆出来，单独标注为"**无论是否做可插拔都必须实现的宿主功能**"，并写明持久化与迁移边界。

**影响**：否则 A1 做完，"重启后布局丢失"会变成用户可见回归。

## 四、改完后的建议顺序

1. 先答第 1 项（Rebirth 定位）——它决定后面所有事；
2. 再改第 2、3 项（结果态、口径）——这两项进入契约定稿；
3. 第 4 项（三块失败域）决定模块数是否仍为 18；
4. 第 5、6 项随 A5/A8 排期处理；
5. 第 7–9 项顺手改。

改完后，双方可以只维护**一张接口表 + 一张对照表**，不再出现两套计数、两套状态、两套"自更新"表述。
