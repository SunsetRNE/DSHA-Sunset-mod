## 0. 一页结论

1. **计数口径完全同意**：逻辑模块 ≠ Gradle 工程 ≠ APK ≠ 运行进程 ≠ 可安装插件。我方口径是 **21 逻辑模块 / 9 个 Gradle 模块 / 1 个 Rust crate / 0 个可安装模块**；你们 18/18/…/可安装插件待定，两边数字根本不能相减。
2. **两套方案目标不同**：你们 18 的骨架是**可插拔模块宿主**（C01 契约 + C02 注册/路由/贡献/停用），这是**新增产品能力**；我方 21 的骨架是**现有单体的状态所有权重构**（谁持有唯一状态、谁有独立失败域），这是**降风险工程**。两者不冲突，但需要先选一个主目标。
3. **若确认要做"可安装模块"**：C01、C02 是我方 21 里**确实没有**的能力，必须补，且不是"再加两个目录"能解决的（涉及模块身份、贡献登记、资源句柄撤销、停用后安全兜底、恢复入口）。
4. **反向缺口共 4 项**：C01 模块协议、C02 宿主核心、F07 Root 模块管理、F08 桌宠与对话窗口。我方清单确实没有这 4 项，逐项见 §2。
5. **两个事实冲突我方已定处理方式**（见 §6）：
   - 你们要求"**Gecko 必须推进**"，而 build359 已整体删除 low/GeckoView 兼容线与 `assembleLowRelease`；
   - 你们写"**Rebirth 候选的正式自更新当前停用**"，而覆盖安装是既有用户唯一的升级路径，停掉等于把 I1–I10 那套维护门禁一起废掉。

## 5. 两个必须先对齐的接口语义（不对齐就会在 FFI/进程边界上丢状态）

**5.1 执行结果态：不是选枚举，是拆正交字段。**

你们 C03 写的是"拒绝、未派发、成功、失败、取消、执行未知"；我方原先用五态 `NOT_SENT / REJECTED / COMPLETED / PARTIAL / UNKNOWN`。两边其实都在用**一个维度**表达**五个独立问题**，所以怎么数都对不齐。

按你们第 3 点意见，我方已改为正交字段（见 §10）：

| 字段 | 取值 | 回答的问题 |
|---|---|---|
| `dispatched` | NOT_DISPATCHED / DISPATCHED / UNKNOWN | 是否派发 |
| `executed` | NOT_EXECUTED / EXECUTED / UNKNOWN | 执行是否确定 |
| `partial` | NONE / PARTIAL / UNKNOWN | 是否部分完成 |
| `effect` | VERIFIED / UNVERIFIED / UNKNOWN / NOT_APPLICABLE | 效果是否验证 |
| `retry` | SAFE / NEEDS_NEW_OBSERVATION / NOT_SAFE / UNKNOWN | 能否重试 |

枚举只作日志/界面的**投影**。这样"取消后可能已执行"不再是 `PARTIAL` 的隐含语义，而是 `dispatched=DISPATCHED` + `executed=UNKNOWN/EXECUTED` + `retry=NEEDS_NEW_OBSERVATION` 的显式组合。

**5.2 一次性派发许可。**

你们 C03 的"派发前撤销可零派发；派发后不能承诺撤回已发生的副作用"我方完全同意。

按你们第 2 点意见，我方已更正表述：`permitMac`（HMAC）**只能验证计划未被无钥输入篡改，不是同进程恶意代码隔离**——同 UID 同进程代码拥有密钥即可自造合法计划；独立进程也不等于独立 UID 权限隔离。它挡的是"误用/被无钥通道改写"，不是"恶意代码"。

因此在首期，**Rust 侧根本没有执行入口**（见 §10 第 1 条），许可机制也随之不进 ABI；将来若真要做执行路径，才需要重新评审这一层，并把它的能力边界写成"防误用，不防同进程恶意代码"。

## 6. 两个事实冲突（需要你们先确认）

**6.1 Gecko —— 我方已定：本轮不恢复。**

你们写"高刷、Gecko、Root 必须推进"、"默认 WebView、可选 Gecko"。但 build359 的事实是：**low 兼容线与 GeckoView 已整体删除**，包括 `assembleLowRelease`、legacy proot/loader、独立上岛包；`minSdk` 固定 30，唯一构建线是 Standard + 系统 WebView。

因此"恢复 Gecko"不是模块划分问题，而是**重新引入一条已退休的构建线**（依赖坐标、变体、资源、测试矩阵、16 KB/ABI 核验、包体积预算）。**我方决定：A06 在本次路径中收窄为"系统 WebView + 能力接口预留"**；如果将来要恢复，需单独立项并给出构建线与测试矩阵的完整方案，不能作为 18 模块方案的隐含前提。

**6.2 自更新。**

你们写"Rebirth 候选的正式自更新当前停用；CI 不是 App 内模块"。
但覆盖安装是既有 Java 版用户升级到新壳的**唯一路径**：同包名、同签名、versionCode 单调；I1–I10 是这条路径上的维护门禁（覆盖后必须进整屏维护页、旧树不得拉起 Web、未确认旧会话只拦自动开始）。

## 7. Rust 引擎在 18 模块里的位置（你们文档未覆盖）

你们的 18 个模块没有提到 Rust。这不一定是错，但需要明确它是"暂不做"还是"已经隐含在某模块里"，否则将来会出现第二套边界。

- **Rust 不占逻辑模块数**，但必须占一条**契约边界**：**三类封闭纯函数**（压缩/摘要/计划校验）+ 正交结果字段；首期**没有** `execute`、`argv`、fd 执行或进程操作（`PlanEnvelope` 仅作类型占位，不进 ABI）。

## 10. 对你们四点意见的回应（2026-11-12）

四点全部采纳，且已改到正式决策记录里（ADR-0004）。逐条对齐：

| # | 你们的意见 | 采纳 | 我方改动 |
|---|---|---|---|
| 1 | 纯计算不该暴露 `execute(PlanEnvelope)` 和 `argv`，应先明确压缩/摘要/计划校验三类封闭接口，别让旁路变成第二套命令执行器 | **完全采纳** | 首期 FFI 只保留三类封闭纯函数：`archive_pack/archive_unpack`、`digest`、`verify_plan`。**删除 `execute(...)` 与 `argv`**；不接收路径字符串、不自行 `open`、不提供 fd 执行与进程/信号操作。`PlanEnvelope`/`permitMac` 退回"将来执行路径"的类型占位，不进 ABI；将来要接执行路径须另立 ADR——那才是你们说的风险点 |
| 2 | HMAC 不是同进程恶意代码隔离；独立进程也不自动等于独立 UID 权限隔离 | **采纳并更正表述** | 撤回"让绕过在类型上不可能"的说法。改为：HMAC 只防**无钥输入**篡改与误用；同 UID 同进程代码拥有密钥即可绕过；独立进程仍是同 UID。对外仍按"非内核沙箱"如实声明，不因引入 Rust 改口 |
| 3 | 五态/六态不是选数字；`PARTIAL` 同时表达"界面未验证"和"取消后可能已执行"会混淆，应拆成五个问题 | **采纳** | 结果模型改为**正交五字段**：`dispatched` / `executed` / `partial` / `effect` / `retry`。枚举只作日志/界面投影；"取消后可能已执行" = `dispatched=DISPATCHED` + `executed=UNKNOWN` + `retry=NEEDS_NEW_OBSERVATION`。C03 的"取消"若保留，应作为**事件**而不是结果态 |
| 4 | `catch_unwind` 兜不住所有原生故障：panic、abort、原生崩溃、JNI 异常、内存生命周期要分别定义边界 | **采纳** | 补了失败域矩阵：可展开 panic → FFI 入口 `catch_unwind` 映射错误码（绝不把 unwind 抛出边界）；abort/原生崩溃/OOM → 不可捕获，进程死亡，靠零/最小 `unsafe` 与有界输入预防；JNI pending 异常 → 每次调用后 `ExceptionCheck` 转 Kotlin 异常；JNIEnv/全局引用/局部帧 → 设计上禁止跨调用持有。高风险任务若需隔离，另立"独立进程"ADR |

**补充一句**：第 1 条还带来一个副作用——既然首期没有执行入口，`permitMac` 也没有存在必要；我们把它从首期 ABI 里拿掉，避免"留着一个用不上的安全机制"被误读成已经实现隔离。等真的要做执行路径时再引入，并同时引入它的能力边界说明。
