## Q8（最关键）：Rebirth 的 `applicationId` 与签名身份是什么？

"隔离实验发行线"回答的是**定位**，但覆盖安装兼容要看**包身份**。三种可能，后果完全不同：

| 选项 | 安装关系 | 数据 | 对 A1–A8 的影响 |
|---|---|---|---|
| **A. 同 applicationId + 同签名** | 装 Rebirth 就是**覆盖正式 DSHA**（用户不会有两个应用） | 正式数据直接进入实验线；实验 bug 会打到真实数据 | I1–I10 必须从第一天生效；versionCode 必须 > 359；每轮发布必进维护页 |
| **B. 独立 applicationId（如 `.rebirth`）+ 同签名** | 可与正式包**共存**，互不覆盖 | 跨线**不继承**（Keystore 别名、会话、`noBackup` 都不共享），只能 v5 导出导入 | I1–I10 只约束 Rebirth 线内部；versionCode 可从 1 起；"不要求换包/卸载"成立 |
| **C. 独立 applicationId + 独立证书** | 同 B，但更像另一个产品 | 同 B，且不能互相覆盖 | 同上，另加一条：更新器与签名核验要分开维护 |

**我方建议是 B**：

- 实验线出错不碰正式数据；
- "不要求正式用户换包或卸载"自然成立；
- 同线内部仍可完整验证覆盖更新与维护门禁（因为 Rebirth 自己迭代时就是覆盖安装）。

## 2. Gecko：放进独立评审，谁执笔？

我方已定：不在 A1–A8 引入 GeckoView 依赖；可作为独立需求保留在 Rebirth 计划范围。建议先给四项预算再决定是否入包：

1. 包体积增量上限；
2. ABI / 最低 API / 16 KB 页兼容；

4. 测试矩阵增量（现有 706 个测试怎么覆盖第二内核）。

**请填**：谁执笔这份评审（你方 / 我方 / 共同）＋ 期望时间点
