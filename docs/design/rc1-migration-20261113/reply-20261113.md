# 给对方的技术回复草稿：RC1 迁移两个问题

> 2026-11-13；草稿，待 Lead 审阅后发送。以下正文可独立使用。内部证据、切片与未验证项见[设计记录](README.md)。本轮未向外发送。

我们按你文档 §5 的两问核对了本仓 build363 对应提交 `d0bc1b0b1e5404539c24da7b8becc3484b5f5f08`，结论如下。这是源码核对与设计意见，生产修复尚未实施。

**第一问：同意收敛为内容副本保护，跨进程绝对原件对象身份明确为 unknown。**

保护目标可以定义为：对本次迁移清单覆盖的文件，迁移前内容已有独立副本，且副本字节读回与记录的大小/摘要一致。dev/ino、mtime、ctime 和路径映射可以发现变化，但不能证明跨进程仍是绝对同一个对象；无需为了这一更强目标默认加入 statx/btime、跨进程持 fd 或新框架。来源被替换与内容副本是否有效应分别报告，unknown 也不能成为删除原件或自动恢复的依据。

这里有一个版本差异要先说清：你文档 §2.1 是暂停草稿，七项 source_stat、stable_read 与 direct rename 的 ctime 例外不能直接套到我们发布脚本。我们当前 [snapshot_row:146–164](https://github.com/SunsetRNE/DSHA-Sunset-mod/blob/d0bc1b0b1e5404539c24da7b8becc3484b5f5f08/app/src/main/assets/rc1-migration.py#L146-L164) 持久化的 sourceIdentity 只有 dev/ino；inventory 另有五项 stat 信息。本次 finalize 的 [385–395](https://github.com/SunsetRNE/DSHA-Sunset-mod/blob/d0bc1b0b1e5404539c24da7b8becc3484b5f5f08/app/src/main/assets/rc1-migration.py#L385-L395) 只在 settings 不存在时转向 imported，再比较 dev/ino 与 SHA，没有草稿的 ctime 比较，也没有将 mapping/links 与旧记录逐项对照。

所以，你的“同内容替换 + mock dev/ino 复用”在我们这条线也存在相同判据缺口：副本和其余输入不变时，静态控制流会让 sourcePreserved/protectionComplete 保持 true；没有 settings 读回账本时会是 pending，不一定 committed。这只证明现有布尔不能用来声称“原对象已证明保留”，不证明真机发生过 inode 复用或数据损坏。本轮未重跑该 mock，也没有把你保留的 46 项草稿结果当作我们的测试结果。

可复用的东西已有：RC1 的分代编号副本与 SHA 读回；backup 层的 NOFOLLOW/同次 FD 核验；PrivateRoots 中已有的宿主迁移状态目录；RetainedCatalogue 的只读保留数据入口。HostDataTransaction 适合显式宿主恢复/树切换时复用维护屏障、先记阶段、保留旧树与写后读回，但 RC1/SettingsForms 目前没有直接跑在它里面，不能宣称已取得整套事务保证。A3 可提供后续投影与校验原则，不是此次修复前置，也不要求引入 Rust 或升级备份格式。我们还发现宿主保留清单与真实 current 记录形状不一致，需要补齐解析与救援回归，不能直接把“已有入口”写成“副本导出闭环已经验证”。

**第二问：Java 缓存应明确返回历史完成，并与 Python、导入器和消费方一起修。**

你列出的 Java 两段与本仓一致：[output():70–82](https://github.com/SunsetRNE/DSHA-Sunset-mod/blob/d0bc1b0b1e5404539c24da7b8becc3484b5f5f08/app/src/main/java/com/deepseekharness/app/runtime/Rc1MigrationCache.java#L70-L82) 直接写成功布尔；[migration():248–280](https://github.com/SunsetRNE/DSHA-Sunset-mod/blob/d0bc1b0b1e5404539c24da7b8becc3484b5f5f08/app/src/main/java/com/deepseekharness/app/runtime/GuestPluginScripts.java#L248-L280) 可以不运行 Python。缓存并非无检查：它本次重新读取私有 current/reuse/receipt、数据根身份、小配置与恢复标记，限制版本和 generation。但它不读全部 snapshot，也不读 settings 分节账本。Python 自己还有 already/cached 短路，因此只修 Java 或只修 Python 都不完整。

现有 [Rc1MigrationResult](https://github.com/SunsetRNE/DSHA-Sunset-mod/blob/d0bc1b0b1e5404539c24da7b8becc3484b5f5f08/app/src/main/java/com/deepseekharness/app/util/Rc1MigrationResult.java#L29-L44) 和 [WebReadyTasks](https://github.com/SunsetRNE/DSHA-Sunset-mod/blob/d0bc1b0b1e5404539c24da7b8becc3484b5f5f08/app/src/main/java/com/deepseekharness/app/core/WebReadyTasks.java#L55-L71) 没有区分 cached 与本次核验，历史成功会用于本次启动/完成判定。不过成功通常被静默处理，不能进一步说 UI 已明文宣称“本次逐一重验全部原件”。

建议的最小结果语义是：

| 情况 | 结果表达与必要检查 |
|---|---|
| 普通启动复用完整旧代，无新迁移写入 | 显式 `historical-complete`、`cached=true`、`verificationScope=historical`；保留原核验时点。本次重查根、输入指纹、generation、契约版本，以及绑定源摘要的 settings 完成账本；不冒充全部副本当前读回 |
| 新输入或明确的新迁移意图 | 当前独立副本完整读回后才能声明 `contentCopyStatus=verified`、`verificationScope=current` 并许可迁移写入。settings 结果只能来自实际写后读回；无 settings 另写 not-required |
| 要用旧副本恢复/继续写入，或要求现在重验 | 先对该代已有副本、清单、输入与账本做只读核对，真正读回后才产生当前证据；不必重新复制来源，不借核对重新导入 |
| 权威记录损坏/缺失、账本矛盾、未知版本或读取异常 | failed/unknown 与明确 reason；保留现场，不能当普通 cache miss 后自动重导 |
| 写入已派发但终态不明、writing 残留、超时/取消/丢回执 | unknown/noReplay；先只读对账。相同可见目标值不能证明未派发，也不能自动再 update 一次 |

原件对象身份单列 `sourceObjectIdentity=unknown`。新结果带版本、phase、startupId/generation；缺字段/非法类型/未知枚举不默认成功。旧 sourcePreserved/protectionComplete 布尔不能无声升级为新保证；若暂留 protectionComplete=true，只能用于本次内容保护已完整核验的分支。消费侧必须同步更新，尤其 Python cached finalize 当前没有输出 protectionComplete，不能只在 Java 消费端加一条该字段必须为 true 的判断。

还要区分两类“失效”：仅 reuse checkpoint 丢失、current/prepare/receipt 与逐节账本完整时，现有 Python 会复用旧代，已 verified 节也不会覆盖后来修改的配置；不应笼统说所有缓存 miss 都会重导。**但 settings-result 单独丢失时，旧 Java 缓存仍可能命中，而 [CJS:79–104](https://github.com/SunsetRNE/DSHA-Sunset-mod/blob/d0bc1b0b1e5404539c24da7b8becc3484b5f5f08/app/src/main/assets/rc1-settings-migration.cjs#L79-L104) 会按新账本重新进入 update；current 缺失也存在新建代次后重导 imported 的路径。** 这是需要修的条件性风险，不是缓存失效应有的恢复策略。

最小落点因此是：cache 探测区分历史命中/确定新输入/优化缓存缺失/权威不可用；prepare/finalize 绑定同次证据且终态不可重复派发；Python 两条快路径与 CJS 账本采用相同语义；parser/启动门禁/鉴权后提示区分历史与当前。另有两个跨层错误应随修复覆盖：cached prepare 不更新磁盘 startupId，后续转 guest finalize 会 stale-startup；损坏 reuse 重建时 Python 可能输出两条结果前缀，Java parser 会拒绝。两者都不应靠自动再做一次掩盖。

我们会把这些作为本仓待评审的最小切片与回归门槛保留。验证需要同时覆盖 Java 真缓存命中、guest Python、真实 SettingsForms、旧账本丢失与未知写入，而不只看 Python 测试。以上意见不承诺合并你们分支，也不将暂停草稿、静态推导或内容副本存在描述成已经完成的生产修复与兼容性证明。
